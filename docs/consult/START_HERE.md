# เริ่ม consult โปรเจกต์แม่หมอกระต่าย

อัปเดต 5 พ.ย. 2026 · เอกสารนี้แยก **สิ่งที่มีจริง** กับ **ข้อเสนอสำหรับงานต่อไป**. ผู้ใช้ยืนยันเป้าหมายให้เว็บดูดวงมี Dashboard ของตัวเอง และภายหลังสั่งสร้างซีรีส์ไพ่เป็นคลิปจากเว็บได้.

## อ่านให้เห็นภาพใน 15–30 นาที

1. [สถานะปัจจุบัน](CURRENT_STATE.md): เปิดเว็บรายวันและหน้า `/reading/`; แยก demo ออกจากระบบตอบที่พร้อมคิดเงิน
2. [Architecture](ARCHITECTURE.md): ทำความเข้าใจเว็บลูกค้า/ห้องทดลอง/Social Center และโครงสร้างเป้าหมาย
3. [Data และ transaction](DATA_AND_PAYMENTS.md): ดู migration จริงก่อนเทียบกับตารางที่เสนอ
4. [Roadmap](ROADMAP.md): งานถัดไปและเกณฑ์ผ่าน; จากนั้นดู [Content Studio](CONTENT_STUDIO.md)
5. [เปิดในเครื่อง](LOCAL_SETUP.md): เว็บรายวันเปิดได้โดยไม่ใช้ key; ห้องทดลองใช้ Supabase ของ dev เอง

## ผลลัพธ์ที่อยากได้จากการ consult

- ตรวจว่าทางเลือก Next.js + Supabase และ worker แยก เหมาะกับขอบเขตนี้หรือไม่
- ช่วยแบ่งงานเป็น PR ที่จบได้จริง พร้อมสิ่งที่ต้องทดสอบ/ประเมินเวลาและค่าใช้จ่ายหลังเห็นโค้ด
- ตรวจแบบข้อมูล/สิทธิ์/การสำรอง ก่อนรวม dashboard และเริ่มรับเงินจริง
- เลือกวิธีรันคิวและ worker สำหรับเสียง/คลิปจากงานทดลองจริงหนึ่งงาน ไม่ตัดสินจากยอดผู้ใช้ที่ยังไม่มีข้อมูล
- เสนอคำตัดสินใจใน issue หรือ [DECISIONS.md](DECISIONS.md); คำแนะนำในเอกสารยังไม่ใช่คำสั่งให้เปลี่ยน production

## คำถามสำหรับรอบคุยแรก

| เรื่อง | ข้อเสนอเริ่มต้น | สิ่งที่อยากให้ช่วยตรวจ |
|---|---|---|
| Repo / แอป | เก็บ monorepo แบบแยกแอปตาม path ปัจจุบันก่อน | ต้องรวม Auth/domain ตอนใด; ทำอย่างไรไม่ให้เว็บฟรีพัง |
| Reading engine | กฎ/ข้อความที่แม่หมออนุมัติ → เทียบกับ LLM เรียบเรียงจากหลักฐานเดียวกัน | แยก scope คำถาม/ตำแหน่ง/ใบขยาย และวัดผลอย่างไร |
| ฐานข้อมูล | Supabase Postgres/Auth/Storage ต่อ; แยกข้อมูล workshop กับลูกค้า | schema, RLS, transaction, backup/restore, dev/staging/prod |
| Payment | เริ่มแพ็กเครดิตต่อคำถาม แล้วค่อยประเมิน subscription | provider เหมาะกับ merchant จริงหรือไม่, refund/failure/webhook |
| Dashboard | Owner ดูเคส/ความรู้/คำสั่งซื้อ/งานคลิป/ต้นทุน | สิทธิ์ role และ workflow review ที่ไม่เปิดข้อมูลเกินจำเป็น |
| Video worker | เริ่มสั่ง template ที่ทำได้อยู่แล้วผ่านคิว | Mac worker สำหรับ pilot หรือ VM/container; ต้องใช้ GPU เมื่อใด |
| Operations | แยก staging และ deploy จาก commit ที่ระบุได้ | CI, rollback, log ที่ไม่ใส่คำถาม/เสียง/secret ของผู้ใช้ |

## ขอบเขตของการส่ง Git รอบนี้

ซอร์สเว็บลูกค้าฉบับ deploy ล่าสุด, ห้องทดลองพร้อม migrations/tests, Social Center ที่รันเฉพาะเครื่อง และ reference ของ pipeline คลิปล่าสุดรวมอยู่ใน repo. เอกสาร source เก่าอาจอ้าง absolute path ของเครื่องเจ้าของ; วิธีเปิดที่ portable ให้ดู `LOCAL_SETUP.md`. เจ้าของเป็นคนให้สิทธิ์ GitHub/Vercel/Supabase แยกกันเมื่อจำเป็น; ไม่ต้องแชร์รหัสหรือใช้บัญชีเจ้าของร่วมกันเพื่อเริ่ม review.

ผลตรวจ source package และข้อจำกัด: [VALIDATION.md](VALIDATION.md).
