## ข้อเสนอหลัก

เริ่มด้วย **ความรู้ที่แม่หมอรับรอง + กฎการอ่าน + ตัวอย่างสำนวน + LLM ช่วยเรียบเรียง** แล้วเปรียบเทียบกับคำตอบจากกฎล้วน. ไม่เริ่มจาก fine-tuning หรือซื้อเครื่องสำหรับ local LLM. ให้ผลทดสอบบอกว่าจำเป็นต้องใช้ AI และปรับอะไรเพิ่ม.

ข้อมูลชุดนี้ใช้เป็นต้นแบบสำนวน แหล่งสกัดวิธีอ่าน และคำตอบอ้างอิงสำหรับตรวจระบบได้. จำนวน 60 เคสเพียงอย่างเดียวไม่ยืนยันว่ารองรับทุกคำถามหรือทุกชุดไพ่. การใส่ตัวอย่างใน prompt หรือค้นความรู้มาให้โมเดลอ่าน ไม่ได้ปรับน้ำหนักโมเดลและไม่ใช่ fine-tuning.

แนวทางนี้เป็นข้อเสนอให้เจ้าของ/แม่หมอตรวจ ไม่ใช่การอนุมัติคำอ่านทั้งหมดโดยอัตโนมัติ. คำสั่งรอบนี้คือวางแผนและอัปเดต handoff; ไม่มีการอนุมัติใช้เงินกับโมเดลหรือเปิดระบบตอบลูกค้าในรอบนี้.

## สิ่งที่จะทำกับข้อมูล

### 1. สำรองและจัดคำอ่านอ้างอิง

- สำรองข้อความ ประวัติ เสียง และ manifest/hash ลง runtime นอก vault ก่อนแปลงข้อมูล. ตัวช่วยเดิม `workshop-standalone/scripts/manage.mjs backup` ดาวน์โหลดเสียงด้วย; JSON export จากหน้า owner อย่างเดียวไม่รวมไฟล์เสียง. ตรวจว่าไม่มีการบันทึกระหว่างสำรองหรือเทียบ revision ก่อน–หลัง และตรวจไฟล์/ลองกู้ในพื้นที่แยกก่อนถือว่า backup ใช้ได้.
- ใช้ `workshop_readings` เป็นคำอ่านปัจจุบันหนึ่งรายการต่อผู้ตอบต่อเคส; ใช้ `workshop_responses` เป็นประวัติ ไม่เอาทุก revision มานับเป็นตัวอย่างใหม่. ผูกกับ `lib/cases.json` ด้วย case ID/version เพื่อคงคำถาม บริบท ช่วงเวลา ไพ่ และตำแหน่ง.
- ถอดเสียง 6 ไฟล์ในเครื่องด้วย `whisper.cpp`/`whisper-cli` แล้วให้แม่หมอตรวจชื่อไพ่และความหมาย. พบ executable `/opt/homebrew/bin/whisper-cli` แล้ว แต่รอบนี้ยังไม่ได้ตรวจไฟล์โมเดล/ทดลองเสียง. เก็บต้นฉบับเสียง ข้อความถอด และข้อความแก้เป็นคนละฉบับ.
- จัดคู่ baseline/followup: baseline ใช้เพียง 3 ใบ; followup มีใบที่ 4 พร้อมคำอ่านเดิมและสิ่งที่เปลี่ยน/ไม่เปลี่ยน. คำอ่านหลังขยายอาจเป็นเพียงส่วนเพิ่มเติม ไม่ควรถือเป็นคำอ่านเต็มแบบแยกจากบริบทเดิม.
- กำหนด `source_case_id`, `source_revision`, `case_version`, `stage`, `split`, `source_type`, `audio_ref`, `review_status`, `approved_by`, `approved_at`, `version`. ปิดข้อมูลส่วนตัวก่อนส่งบริการภายนอก. ไม่บันทึกอีเมล เสียง หรือคำอ่านดิบลง public repository.

ผลส่งมอบ: สำรองที่ตรวจได้ + ชุดคำอ่านอ้างอิงที่มีที่มา + รายการจุดที่ต้องให้แม่หมอตรวจ. งานส่วนนี้ยังไม่ทำในรอบวางแผน.

### 2. แยกความรู้กับสำนวน และให้แม่หมอรับรอง

ใช้ **development 40 เคสเท่านั้น** สำหรับพัฒนา:

| ส่วน | ต้องเก็บอะไร | ใช้อย่างไร |
|---|---|---|
| วิธีตีความ | ความหมายตามไพ่/ตำแหน่ง/หมวด/เงื่อนไข, วิธีเชื่อมไพ่, วิธีขยายอนาคต, สิ่งที่ห้ามสรุป | เป็นข้อจำกัดและเนื้อหาที่ระบบอนุญาตให้นำมาตอบ |
| สำนวน | วิธีเปิด–สรุป, สรรพนาม, ความยาว, ระดับการฟันธง, คำที่ใช้/ไม่ใช้, วิธีให้คำแนะนำและถามกลับ | เป็น style guide และตัวอย่างภาษาสั้น ๆ โดยไม่ยืมข้อสรุปของเคสอื่น |
| ตัวอย่างอ้างอิง | คำถาม+บริบท+ไพ่+คำอ่านที่ตรวจแล้ว พร้อมแหล่งที่มา | ใช้ตรวจพฤติกรรมและเป็น few-shot examples ที่ตรงงาน |

สิ่งที่สกัดเป็น **ข้อเสนอให้ตรวจ** จนกว่าแม่หมอจะรับรอง. ห้ามเดากฎจากคำตอบสั้น ๆ แล้วบันทึกว่าเป็นความรู้ของแม่หมอ. ถ้าขาดเหตุผล ให้ถามเพิ่มเฉพาะกฎนั้น พร้อมเคสที่เกี่ยวข้อง ไม่บังคับกรอกใหม่ทั้งชุด. ต้นฉบับที่ส่งแล้วคงเดิม; ฉบับรับรองแก้ได้ด้วยการออก version ใหม่.

เพิ่มหน้า owner review ที่ดูต้นฉบับ/ฟังเสียง/แก้ฉบับรับรอง/รับรองหรือปฏิเสธได้. Owner ตอบและรับรองงานของตนเองได้ตามที่เจ้าของต้องการ; `submitted/review` ยังแยกจาก `approved` และ `rejected`. สิทธิ์ owner มีแล้ว แต่ workflow การรับรองนี้ยังไม่สร้าง.

ผลส่งมอบ: `style_profile_v1`, knowledge/rules ที่รับรอง, ตัวอย่าง development ที่เลือกแล้ว, coverage matrix และรายการความรู้ที่ยังขาด. ไม่ตั้งชื่อสไตล์ว่า “อ่อนโยน/ฟันธง/ปลอบใจ” จนกว่าจะตรวจเนื้อหาจริงและแม่หมอยืนยัน.

### 3. สร้างฟังก์ชันตอบแบบควบคุมขอบเขต

เส้นทางเสนอ:

```text
คำถาม + บริบท + ไพ่/ตำแหน่ง
  → ตรวจขอบเขตและข้อมูลที่ขาด
  → ค้นกฎ/ความรู้ที่แม่หมอรับรองและใช้ได้กับกรณีนี้
  → เตรียมสาระคำอ่านจากหลักฐาน
  → A: เรียงตาม template หรือ B: ให้ LLM เรียบเรียงตาม style guide
  → ตรวจผลและหลักฐาน → ตอบ / ถามเพิ่ม / ส่งคิว owner
```

สัญญาฟังก์ชันสำหรับ Claude ออกแบบต่อ (ยังไม่ใช่ implementation):

```ts
type ReadingDecision = {
  status: 'answered' | 'clarify' | 'needs_owner' | 'out_of_scope';
  answer: string | null;
  clarification: string | null;
  evidenceIds: string[];
  knowledgeVersion: string;
  styleVersion: string;
};
// generateReading({question, category, intent, context, horizon,
//   stage, cards: [{id, position, orientation}], baselineReading?})
//   -> ReadingDecision
```

- **เครื่องมือ:** Next.js/TypeScript เดิมสำหรับ API, Supabase Postgres สำหรับความรู้ที่รับรอง/สถานะ/คิวตรวจ, `whisper.cpp` เฉพาะขั้นเตรียมเสียง, LLM API ผ่าน adapter สำหรับวิธี B, schema validation ฝั่ง server และชุดประเมินในโปรเจกต์.
- เริ่มค้นด้วย metadata เช่นหมวด/เจตนาคำถาม/card ID/ตำแหน่ง/เงื่อนไข และลำดับความเหมาะสม. ชุดเริ่มต้นเล็ก ยังไม่จำเป็นต้องเพิ่ม vector database, embedding service, LangChain หรือ local LLM server. ค่อยเพิ่ม semantic retrieval เมื่อการทดสอบชี้ว่าค้นไม่เจอคำถามที่ความหมายเดียวกัน.
- บทบาท LLM คือเรียบเรียงจากสาระที่อนุญาตและตัวอย่างภาษา ไม่ใช่สร้างข้อสรุปดูดวงจากความรู้ทั่วไปของโมเดล. Prompt อย่างเดียวไม่รับประกันว่าจะไม่แต่ง; ต้องตรวจผลและมี fallback.
- ห้ามคืนคำตอบเก่าทั้งชิ้นเพียงเพราะคำถามคล้ายกันหรือไพ่ตรง 1–2 ใบ. แยกข้อเท็จจริงของเคสตัวอย่างออกจากหลักการที่ใช้กับผู้ใช้ใหม่ได้จริง. ไพ่เหมือนกันแต่คำถาม/ตำแหน่ง/บริบทต่างกันต้องประเมินใหม่; ไพ่เหมือนกันและบริบทเดียวกันควรคงสาระเดียวกัน ไม่สุ่มเปลี่ยนคำทำนายเพื่อให้ดูฉลาด.
- เปิดพิมพ์คำถามได้ภายในหมวดและขอบเขตที่รองรับ. ข้อมูลกำกวม → `clarify`; อยู่ในงานดูไพ่แต่ไม่มีหลักฐานพอ → `needs_owner`; นอกบริการ → `out_of_scope`. ไม่เอาคะแนนความมั่นใจที่โมเดลรายงานเองเป็นเกณฑ์เดียว.
- ตรวจ ID/จำนวนไพ่/ตำแหน่งฝั่ง server; baseline ห้ามมีข้อมูลใบ 4. Followup ต้องขยายอนาคตตามกฎที่รับรอง ไม่เปลี่ยนคำอ่านต้นฉบับย้อนหลัง.
- ตรวจ schema, evidence ID ที่อยู่ในชุดอนุมัติ, เงื่อนไขของกฎ, ข้อสรุปที่เกินหลักฐาน, ความขัดแย้ง และภาษาที่แม่หมอห้ามใช้. การมี evidence ID ไม่ได้พิสูจน์ว่าข้อความตรงหลักฐาน ต้องทดสอบการเชื่อมโยงข้ออ้างด้วย.
- เมื่อ LLM timeout/ล่ม/ผลตรวจไม่ผ่าน ใช้วิธี A เฉพาะเมื่อมีหลักฐานเพียงพอ; หากไม่พอต้องส่งคิว owner. คิวต้องมีสถานะติดตามและวิธีแสดงให้ผู้ใช้ทราบ งานส่วนนี้ยังไม่พร้อมในเว็บลูกค้า.
- รูปไพ่ การสับ และหน้าอ่านเดิมใช้ต่อได้. จุดเปลี่ยนคือ `web/tarot/lib/reading.ts:createReading()` ซึ่งตอนนี้ยังคืน `status: 'demo'`, กับ `app/reading/page.tsx` ที่เรียกใน browser. ฟังก์ชันจริงต้องเรียก server-side API; ห้ามนำ service key หรือ model key ลง browser. เว็บลูกค้าปัจจุบันเป็น static export จึงต้องเพิ่มบริการ API แยกหรือเปลี่ยน deployment ให้รองรับ server ก่อนเชื่อมจริง.

### 4. เปรียบเทียบ A/B ด้วยโจทย์เดียวกัน

- **A:** กฎ + template จากความรู้ที่แม่หมอรับรอง ไม่ใช้ LLM.
- **B:** ใช้สาระและหลักฐานชุดเดียวกับ A เพิ่ม LLM เรียบเรียงตาม style guide และตัวอย่าง development. Luna เป็นตัวเลือกจากแผนเดิม ต้องตรวจ model ID/สิทธิ์บัญชี/ราคา/คุณภาพไทยก่อนทดลอง; ไม่ถือว่าตัวเลือกนั้นใช้งานได้เพียงเพราะเคยระบุชื่อไว้.
- เตรียม A และหน้าเทียบก่อนเรียกโมเดลได้. ช่อง B ให้แสดงว่ายังไม่สร้างจนกว่าจะมีผลโมเดลจริง ไม่ใส่คำอ่านแม่หมอหรือข้อความแต่งมือแล้วอ้างว่าเป็น AI.
- เริ่มทดลองบน development กลุ่มเล็กที่ครอบคลุมทั้ง 4 หมวด/สองช่วง ตั้งเพดานจำนวนคำขอและเงินก่อนรัน เก็บ model/prompt/knowledge/style version, latency, token usage และค่าใช้จ่ายจริง. ยังไม่อนุมัติงบหรือเรียก API ในรอบนี้.
- แม่หมอเห็นโจทย์ ไพ่ และคำตอบสองด้านโดยสุ่มซ้าย–ขวา ปิดชื่อวิธี ให้เลือก A/B/เสมอ/ไม่ผ่านทั้งคู่ พร้อมแก้ประโยคที่อยากใช้. ให้คะแนนแยก “ตรงวิธีอ่าน”, “สำนวนเหมือนแม่หมอ”, “ตรงคำถาม”, “ไม่แต่งเกินข้อมูล”, “ใบขยายเชื่อมถูก”. ดูต้นฉบับอ้างอิงหลังให้คะแนนรอบแรกเพื่อลดการยึดถ้อยคำเดิม.
- ประเมินความถูกต้องก่อนความชอบภาษา. บันทึกทั้งคู่และ feedback เป็นข้อมูลรอบต่อไป; ข้อมูลเปรียบเทียบที่ดีค่อยพิจารณาใช้ฝึกในอนาคตได้.

### 5. สอบด้วย holdout และเปิดเฉพาะขอบเขตที่ผ่าน

- คง 20 holdout แยกจาก retrieval, prompt examples, style extraction และการสกัดกฎทั้งทางตรงและทางอ้อม. ถอดเสียง/ตรวจคำผิดเพื่อเตรียมคำตอบอ้างอิงได้ แต่ห้ามส่งเนื้อหาไปขั้นพัฒนาระบบ.
- หลังล็อกวิธี/prompt/knowledge version จึงประเมิน holdout. ในขั้นสร้างคำตอบห้ามเห็นคำตอบอ้างอิง; ใช้ในขั้นให้คะแนนเท่านั้น. หากใช้ความผิดพลาดชุดนี้แก้ระบบแล้ว ต้องระบุว่า holdout ถูกใช้พัฒนา และจัดชุดสอบใหม่ก่อนอ้างผล unseen.
- เพิ่มเคสนอกขอบเขต คำถามกำกวม ไม่มีความรู้รองรับ คำสั่งหลอกให้ข้ามกฎ ข้อมูลขัดแย้ง และการเปิดใบที่ 4; 60 เคสเดิมอย่างเดียวไม่ได้พิสูจน์พฤติกรรมเหล่านี้.
- เกณฑ์เสนอสำหรับ pilot: ไม่มีข้อผิดพลาดร้ายแรงในชุดตรวจที่กำหนด (ไพ่/ตำแหน่งผิด, เห็นใบขยายก่อนเวลา, แต่งเรื่องส่วนตัว, หลุดขอบเขต); owner รับคำตอบอย่างน้อย 18/20 เคส holdout และคะแนนสำนวนเฉลี่ยอย่างน้อย 4/5. นี่คือเป้าทดลองที่ต้องยืนยัน ไม่ใช่ผลที่ได้แล้วหรือหลักฐานความแม่นในการทำนายอนาคต.
- รายงานอัตราตอบได้/ถามเพิ่ม/ส่ง owner แยกจากคุณภาพคำตอบที่ตอบสำเร็จ เพื่อกันระบบ “ผ่าน” ด้วยการส่งทุกเคสให้คน. แสดงผลรายหมวดเพราะจำนวนตัวอย่างน้อย; 20 เคสไม่พิสูจน์คุณภาพ 100% ในผู้ใช้จริง.
- ถ้าวิธี B ชนะด้านภาษาโดยไม่ลดความถูกต้อง และต้นทุน/เวลารอรับได้ จึงเปิด B ในขอบเขตที่ผ่าน. ถ้าไม่ชนะ ใช้ A หรือทบทวนข้อมูลก่อน. เตรียม feature flag, rate limit, timeout, ประวัติคำตอบ/รุ่น และคิว owner ให้พร้อมก่อน beta.

## เหตุผลที่ยังไม่เริ่ม fine-tuning

ตอนนี้สิ่งที่ขาดคือความรู้ที่ตรวจและรับรองแล้ว กฎที่อธิบายได้ และผลประเมิน. Fine-tuning อาจช่วยพฤติกรรมหรือสำนวนในภายหลัง แต่ไม่เติมความรู้ที่แม่หมอยังไม่ได้ให้ และไม่รับประกันว่าจะปฏิเสธคำถามนอกขอบเขตได้ถูกต้อง. 60 เคสเป็นจุดเริ่มทดลองที่มีประโยชน์ ไม่ควรอ้างว่าเพียงพอหรือไม่พอสำหรับทุกเทคนิคจากจำนวนอย่างเดียว. แนวทางประเมิน → ปรับ prompt/บริบท → พิจารณาการฝึกเมื่อมีหลักฐาน สอดคล้องกับ [OpenAI model optimization](https://developers.openai.com/api/docs/guides/model-optimization) และ [RAG กับ fine-tuning](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy).

ข้อจำกัดแพลตฟอร์มที่ตรวจล่าสุด 26 ต.ค. 2026: [OpenAI supervised fine-tuning](https://developers.openai.com/api/docs/guides/supervised-fine-tuning) ระบุว่าแพลตฟอร์ม fine-tuning ไม่เปิดให้ผู้ใช้ใหม่ และกำลังยุติบริการตามกำหนดของโมเดลเดิม. ไม่ควรผูก roadmap ใหม่กับบริการนั้น. หากภายหลังมีเหตุผลต้องฝึก ต้องเลือก provider/open-weight ที่รองรับจริงและประเมินต้นทุนใหม่. ข้อนี้ไม่ใช่ข้อสรุปว่า LLM API สำหรับสร้างข้อความใช้ไม่ได้.

พิจารณาการฝึกเมื่อมีหลักฐานว่าความรู้/การค้นถูกแล้ว แต่ยังผิดสำนวนหรือพฤติกรรมซ้ำ ๆ แม้ปรับ prompt และตัวอย่าง และมีข้อมูลที่รับรองกับชุดสอบใหม่มากพอให้วัดผลคุ้มทุนได้. ไม่มีจำนวนขั้นต่ำตายตัวที่รับประกันคุณภาพในงานนี้.
