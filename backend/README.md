## ลำดับงานที่ยืนยัน — owner ทดสอบก่อน แล้วเตรียมเปรียบเทียบคำอ่าน (2026-10-21)

เจ้าของระบุบัญชีแม่หมอที่มีอยู่แล้วให้เป็น owner ของเว็บทดลอง ใช้บัญชีเดียวตอบ อัดเสียง และทบทวนงาน. เปลี่ยนเฉพาะ `workshop_members.role` จาก reader เป็น owner และอ่านกลับยืนยัน: สมาชิก active 1 owner / 1 reader. ไม่เปลี่ยนรหัสผ่าน คำอ่าน เสียง หรือสิทธิ์บัญชีอื่น; ไม่บันทึกอีเมล/รหัสผู้ใช้ลง repository. ตรวจ login และหน้าสิทธิ์ owner บน URL production ผ่าน ดู [ผลตรวจ](../web/workshop-standalone/VALIDATION.md).

**ขอบเขตปัจจุบัน:** owner บันทึกคำอ่านของตัวเอง ดูคำอ่านสมาชิกอื่น และส่งออกได้. คำอ่านที่ส่งแล้วล็อกต้นฉบับ; ยังไม่มีปุ่มรับรองคำอ่านเป็นความรู้ approved, การแก้ฉบับรับรอง, หน้าเปรียบเทียบ หรือการเชื่อม Luna. สิทธิ์ owner ในแอปไม่ใช่การโอนบัญชี Supabase/Vercel. “ส่งทบทวน” ยังไม่เท่ากับ “อนุมัติใช้ตอบลูกค้า”.

**คำสั่งลำดับงาน:** ให้แม่หมอทดสอบและเก็บคำอ่านในเว็บปัจจุบันให้เสร็จก่อน แล้วจึงเริ่มเตรียมตัวเปรียบเทียบสองวิธี. รายละเอียดด้านล่างเป็นแผนที่เสนอ ยังไม่ได้สร้างตัวเปรียบเทียบหรือเรียก AI ในรอบนี้.

| เฟส | งานและผลส่งมอบ | ใช้ Luna หรือไม่ |
|---|---|---|
| 1 — แม่หมอทดสอบ | อ่าน 3 ใบก่อนเห็นใบขยาย บันทึกเสียง/ข้อความ จากนั้นอ่านใบ 4 และส่งทบทวน; ตรวจฟังคืน/รีเฟรช/มือถือจริง พร้อมแจ้งโจทย์หรือ UI ที่ต้องแก้ | ไม่ใช้ |
| 2 — เตรียมความรู้และคำตอบอ้างอิง | ถอดเสียงในเครื่อง ตรวจข้อความกับแม่หมอ แยกความหมาย กฎอ่านร่วมกัน สำนวน และสิ่งที่ห้ามสรุป; เพิ่มการรับรองโดย owner และเก็บฉบับแก้แยกจากต้นฉบับพร้อมรุ่น | ไม่ใช้ |
| 3 — เตรียมเครื่องมือเปรียบเทียบ | ทำวิธี A ด้วยกฎและข้อความที่อนุมัติ เตรียมช่องคำตอบซ้าย/ขวา แบบให้คะแนน ประวัติรุ่น และวิธีสุ่มฝั่ง; ช่องวิธี B รอผลทดลองจริง ห้ามใส่ข้อความจำลองแล้วระบุว่าเป็นผล Luna | ไม่ใช้ |
| 4 — ทดลอง AI ขนาดเล็ก | สร้างวิธี B ด้วย Luna จากคำถาม ไพ่ บริบท รุ่นความรู้ และโครงหลักฐานเดียวกับ A; ให้แม่หมอเทียบโดยซ่อนชื่อวิธีและบันทึกผล | ใช้เฉพาะรอบทดลองที่ตกลงแล้ว |
| 5 — ตัดสินใจเปิดใช้ | ดูคุณภาพ ความผิดพลาด เวลา และต้นทุน เทียบกับ A; หาก B ไม่เพิ่มประโยชน์ ใช้ A ต่อได้โดยไม่เปลี่ยนหน้าไพ่หรือรื้อคลัง | ยังไม่เท่ากับเปิด AI ให้ลูกค้า |

### ความหมายของการเทียบสองวิธี

- **A:** ระบบกฎและประโยคของแม่หมอที่รับรองแล้ว ต้องรองรับตำแหน่งและใบขยายตามขอบเขตที่ทดสอบ ไม่ใช้ summary demo เดิมที่ยังไม่มีตรรกะเป็นคู่เทียบเพื่อให้ B ดูดีกว่า.
- **B:** โครงหลักฐานเดียวกับ A แล้วให้ Luna เรียบเรียง ตรวจว่ามีการเติม เปลี่ยน หรือตัดสาระหรือไม่. การทดลองนี้วัดประโยชน์ของการเรียบเรียง ไม่สรุปว่าโมเดลตีความไพ่ได้ถูกต้องทุกแบบ.
- คำตอบตรงจากแม่หมอเป็นคำตอบอ้างอิงสำหรับตรวจ ไม่ใช่ B ที่แสร้งว่าได้จาก AI. ยังไม่ใช่การ fine-tune โมเดล.
- **เตรียมเครื่องมือก่อนใช้ Luna ได้ แต่การเปรียบเทียบ A กับ B จริงต้องมีการเรียก Luna เพื่อสร้าง B ก่อน.** รอแม่หมอทดสอบเสร็จตามคำสั่ง แล้วเตรียมข้อมูล/หน้าเปรียบเทียบก่อนรอบ API เล็ก; ไม่เปิด chatbot ให้ลูกค้าระหว่างเตรียม.

### การแบ่งข้อมูลและหน้าให้แม่หมอตรวจ

- คง 40 development / 20 holdout ตาม `lib/cases.json` และไม่แยก family ข้ามชุด. กฎ/ตัวอย่างจาก development ใช้พัฒนาได้; คำตอบอ้างอิง holdout ใช้ให้คะแนนเท่านั้น ไม่ส่งเป็น prompt หรือ retrieval ของ A/B.
- เมื่อแม่หมอทดสอบครบ ต้องตรวจความครอบคลุมของความหมายและกฎอีกครั้ง การส่งครบ 60 เคสไม่ใช่หลักฐานว่าพร้อมเปิดขายทุกหมวด/ทุกไพ่.
- หน้าตรวจแสดงโจทย์ บริบท และไพ่ชุดเดียวกัน พร้อมคำตอบซ้าย/ขวาที่สุ่มชื่อวิธีและตรึงไว้ต่อการประเมิน; ยังไม่เฉลยว่า A/B จนส่งคะแนน. มีตัวเลือกซ้ายดีกว่า/ขวาดีกว่า/พอ ๆ กัน/ไม่ผ่านทั้งคู่ และช่องแก้ข้อความพร้อมเหตุผล.
- ให้คะแนนแยกความตรงไพ่และตำแหน่ง ความตรงคำถาม การเชื่อมใบขยาย สำนวน และการเพิ่มข้อสรุปที่ไม่มีหลักฐาน. เก็บรุ่นความรู้/กฎ/prompt/model เวลาและต้นทุน เพื่อทำซ้ำได้.
- ตรึงคำตอบและเกณฑ์ก่อนเปิดชุด holdout. ถ้าใช้ผล holdout มาแก้กฎหรือ prompt แล้ว ต้องมีชุดตรวจใหม่ก่อนอ้างผลกับข้อมูลที่ไม่เคยใช้พัฒนา. คะแนนความชอบ/ความตรงใจไม่ใช่หลักฐานยืนยันเหตุการณ์อนาคต.
- การทดลอง API ใช้เฉพาะเคสสมมติและความรู้ที่อนุมัติให้ใช้ ไม่ส่งเสียงต้นฉบับ ชื่อ อีเมล หรือเรื่องส่วนตัวของลูกค้าตามกติกาโปรเจกต์. รอบนี้ไม่ใช้ API และไม่มีค่าโมเดลเกิดขึ้น.

## ต้องแก้ก่อนเก็บเงินจริง

1. **ความหมายไพ่หลุดฝั่ง browser:** `lib/reading-cards.json` (468 ข้อความ) ถูก bundle ไปกับ `/reading/` ใครเปิด source ก็อ่านได้โดยไม่จ่าย ต้องย้ายความหมายไว้บน server และส่งคืนเฉพาะ reading ที่มีสิทธิ์ (`entitlements`) เท่านั้น
2. **ไพ่ต้องถูกบันทึกบน server ก่อนจ่าย:** คำอ่านที่ขายต้องคำนวณจากไพ่ที่ server บันทึกไว้ (`reading_cards`) ไม่ใช่ไพ่ที่ browser ส่งมาตอนปลดล็อก
3. **ปุ่มปลดล็อก demo:** เปลี่ยนเป็น flow สั่งซื้อจริง ยืนยันผลจาก webhook ของผู้ให้บริการ ไม่ใช่จากหน้าเว็บ
4. **PDPA:** นโยบายความเป็นส่วนตัว ข้อกำหนดการใช้ ความยินยอม (`consents`) การลบบัญชีและลบคำถามที่พิมพ์
5. **คอนเทนต์ที่ขาย:** ภาพไพ่ที่เหลือ 73 ใบ, ความหมายที่เจ้าของอนุมัติ, วิธีอ่าน 3 ใบของเจ้าของ (หรือเปิดตัวเฉพาะหมวดความรักก่อน)

| รับเงิน | payment gateway ไทยเจ้าเดียวที่รองรับ PromptPay QR, TrueMoney Wallet และ LINE Pay พร้อม webhook (เช่น Opn Payments/Omise, 2C2P, GB Prime Pay) | ต้องเช็กว่ารองรับครบ ค่าธรรมเนียม และเงื่อนไขเปิดร้านค้า ณ วันสมัคร; โอนเข้าบัญชีตรงใช้สลิปให้แอดมินตรวจ |

หลักออกแบบ

- **เงิน:** เก็บเป็นสตางค์ (`1900` = 19 บาท) ราคาที่ลูกค้าจ่ายจริงคัดลอกไว้ใน `order_items` จึงไม่เปลี่ยนตามการแก้ราคาภายหลัง
- **บริการใหม่:** ทุกบริการอยู่ใน `services` กำหนด `draw_access` (ใครเริ่มได้) กับ `result_access` (ใครดูผลได้) แยกกัน; ไพ่ 3 ใบ = เริ่มได้โดยไม่ login แต่ดูผลต้องจ่าย
- **ดูก่อน login:** reading ผูกกับ `anonymous_visitors` แล้วย้ายเข้าบัญชีเมื่อ login เพื่อจ่ายเงิน
- **สิทธิ์ดูผล:** server ส่งคำอ่านเมื่อมีแถวใน `entitlements` เท่านั้น (ได้จากการซื้อ เครดิต โปร หรือแอดมิน)
- **ความรู้ของเจ้าของมีรุ่น:** `knowledge_versions` + `review_status` แก้ความหมายได้โดยคำอ่านที่ขายไปแล้วยังเป็นข้อความเดิม (`reading_results`)
- **event/ธีม:** event ชี้ไปยังธีม ธีมเก็บ `ui_tokens` และ `theme_assets` (โมเดลมาสคอต หลังไพ่ เสียง); reading บันทึก event/ธีมที่ใช้ เพื่อวัดผลแต่ละ event
- **PDPA:** คำถามที่พิมพ์และรูปเป็นข้อมูลส่วนบุคคล ลบได้; ลบบัญชีใช้ `deleted_at` + ล้างข้อมูล แต่เก็บธุรกรรม; คู่แข่งเก็บเฉพาะข้อมูลสาธารณะระดับบัญชี/โพสต์ และสรุปธีมคอมเมนต์รวม ไม่เก็บรายบุคคล

ข้อที่ต้องทำใน migration จริง (DBML แสดงไม่ได้)

- `bookings` กันจองซ้อนด้วย `EXCLUDE USING gist` บนช่วงเวลาต่อแม่หมอ
- unique ของ `card_meanings` มีคอลัมน์ที่เป็น null ได้ ให้ใช้ `NULLS NOT DISTINCT`
- `app_events` แบ่ง partition รายเดือน; ตารางของผู้ใช้เปิด Row Level Security ถ้าใช้ Supabase

ตรวจแล้ว: แปลง DBML เป็น SQL ด้วย `@dbml/cli@10.2.0` และรันบน PostgreSQL ผ่าน `@electric-sql/pglite@0.5.8` ได้ 66 ตาราง, 118 foreign key, 16 enum; ทดลองสั่งซื้อไพ่ 3 ใบ 19 บาทจ่ายด้วย TrueMoney และการใส่ไพ่ซ้ำในการดูครั้งเดียวถูกปฏิเสธ

### ตัวอย่าง flow ไพ่ 3 ใบ

1. ผู้เข้าชมสับและวางไพ่: `readings` (ยังไม่มี `user_id`) + `reading_cards`
2. กดดูความหมาย: login (LINE/Google/username) แล้วย้าย reading เข้าบัญชี
3. สร้าง `orders` + `order_items` (1900 สตางค์) → `payments` ตามวิธีที่เลือก → webhook ยืนยัน → `orders.paid` → `entitlements`
4. server สร้าง `reading_results` จากความหมายรุ่นที่เผยแพร่ → `readings.unlocked` → อัปเดต `user_daily_summaries` สำหรับปฏิทิน
5. ผู้ใช้บันทึกและแชร์: `journal_entries` (private → unlisted/community) → `journal_reactions`, `journal_comments`

### หน้าที่ใบที่ 4 และ flow ที่เสนอ

ชื่อฟีเจอร์: **“ขยายแนวโน้มอนาคต”**. หน้าที่คงที่: **ปัจจัยหรือเงื่อนไขที่ช่วยอธิบายแนวโน้มจากใบที่ 3**. ต้องให้เจ้าของอนุมัติวิธีอ่านและตัวอย่างก่อนใช้ขาย.

1. เลือกหมวด สถานะ เจตนาคำถาม และช่วงเวลาที่ต้องการพิจารณา; ถ้าคำถามมีหลายประเด็น ให้เลือกประเด็นเดียวก่อนเริ่ม.
2. สับและเลือกอดีต/ปัจจุบัน/อนาคตเหมือนเดิม. ตรึงไพ่ทั้งสามและข้อมูลคำถามเมื่อเริ่มอ่าน.
3. หลังอ่านสามใบ มีปุ่มเปิดใบขยายได้หนึ่งครั้งจาก 75 ใบที่เหลือในสำรับเดิม. ใบที่ 4 ใช้กฎขยายเฉพาะใบที่ 3; การรีเฟรช/กดซ้ำต้องคืนใบเดิม.
4. แสดงข้อความต่อจากอนาคต: “ใบนี้ช่วยขยายว่า…” และสรุปใหม่โดยรักษาคำอ่านสามใบเดิม. เก็บผลก่อนและหลังเพิ่มใบแยก revision เพื่ออธิบายได้ว่าเปลี่ยนส่วนใด.
5. หากไพ่ชี้คนละทิศ ให้อธิบายแรงสนับสนุนกับเงื่อนไขที่ขัดกัน. ไม่ลบความหมายใบอนาคต ไม่สรุปว่าบวกหนึ่งใบหักล้างลบหนึ่งใบ และไม่เปิดเพิ่มวนจนได้ผลที่ถูกใจ.

**ข้อเสนอ UX:** รวมสิทธิ์ใบขยายในราคาคำถามตั้งแต่แรก และแสดงตั้งแต่ก่อนจ่าย. ไม่ผูกปุ่มขายเพิ่มกับการได้ไพ่ที่ชวนกังวล. ความหมายของใบที่ 4 ไม่ใช่คำรับรองว่าพยากรณ์แม่นขึ้น.

| ความหมายหลัก | ไพ่, ตั้งตรง/กลับหัว, แก่น, แง่สนับสนุน, แง่ท้าทาย | ห้ามเปลี่ยนแก่นตามคำถามเพื่อเอาใจ |
| หมวดและสถานะ | love/work/money/life; โสด/คุยกัน/มีแฟน ฯลฯ | จำกัดความหมายให้ตรงบริบท |
| ตำแหน่ง | past/present/future/future_clarifier | อดีตเป็นพื้นหลัง; ปัจจุบันเป็นพลวัต; อนาคตเป็นแนวโน้มมีเงื่อนไข |
| เจตนาคำถาม | feelings/commitment/breakup/reconcile/direction/choice | เลือกประเด็นที่จะตอบ ไม่ดึงทุกความหมายมาใส่ |
| กฎประกอบ | ไพ่/กลุ่มสัญญาณ + ตำแหน่ง + ขอบเขตที่ใช้ได้ + ข้อสรุปที่อนุญาต | เชื่อมใบ 3–4 และทั้งชุดอย่างตรวจสอบได้ |
| หลักฐานและการอนุมัติ | source, version, reviewer, review status | เผยแพร่เฉพาะความรู้ที่ approved |

**ตัวอย่างออกแบบ ไม่ใช่คำอ่านที่อนุมัติ:** The Fool ในบริบทคนคุยมีแก่นตามคลังว่า “คุยสนุกแต่ยังไม่คิดไกล”. ตำแหน่งอดีตอาจชี้รูปแบบการเริ่มต้นที่ยังไม่วางแผน; ปัจจุบันชี้ความสัมพันธ์ที่ยังเปิดกว้าง; อนาคตชี้ความเป็นไปได้ที่จะลองก้าวใหม่โดยความผูกมัดยังไม่ชัด. ไม่ควรอนุมานว่าอีกฝ่ายนอกใจหรือจะเลิกโดยไม่มีฐานรองรับ. เจ้าของต้องทบทวนการแปลงตามตำแหน่งเหล่านี้ก่อนบันทึกเป็น approved. แหล่งแก่นเดิม: [[tarot-the-fool]].

ลำดับการตอบที่เสนอ:

`ล็อกคำถาม/ไพ่ → จัดเจตนาและขอบเขต → เลือกความหมายที่อนุมัติ → ประเมินกฎประกอบ → สร้างโครงคำตอบพร้อมหลักฐาน → เรียบเรียง → ตรวจข้ออ้าง → บันทึกผล`

- เริ่มจากหมวดความรักที่มีข้อมูล; ไม่เปิดขายหมวดที่ไม่มีความหมายและกฎพร้อมใช้งาน.
- v1 ใช้กฎและประโยคต้นแบบที่เจ้าของอนุมัติได้โดยไม่ต้องเรียก AI API. ถ้าใช้ AI ให้ช่วยจัดภาษาในขอบเขตหลักฐาน ไม่ให้สร้างคำทำนายหรือเหตุผลใหม่. การมี `meaning_id` อ้างท้ายประโยคยังไม่พิสูจน์ว่าประโยคนั้นถูกฐานข้อมูลรองรับ ต้องตรวจเนื้อหาด้วย.
- แต่ละข้อสรุปมีรายการหลักฐาน: ไพ่, ตำแหน่ง, meaning ID, rule ID และรุ่นความรู้. ถ้าไม่มีความรู้สำหรับบริบท ต้องแจ้งช่องว่างหรือถามเพิ่ม; ห้ามดึงหมวดอื่นมาเติม.
- จัดสัญญาณเป็นคนละแกน เช่น ความใกล้ชิด ความพร้อมผูกมัด ความขัดแย้ง ความชัดเจน และการเว้นระยะ. หลีกเลี่ยงคะแนนดี/ร้ายรวมเพียงตัวเดียว. ไพ่ใบเดียวอาจสะท้อนความรู้สึกดี แต่ความพร้อมผูกมัดต่ำ.
- แยก “คำอ่านชี้ทิศเดียวกัน/มีทั้งสองด้าน/ข้อมูลยังไม่พอ” ออกจากโอกาสเกิดเหตุการณ์จริง; ไม่แสดงเปอร์เซ็นต์รัก/เลิกที่ไม่มีการสอบเทียบ.
- คำถามเดิม ไพ่เดิม บริบทและรุ่นความรู้เดิม ต้องได้สาระเดิม. เก็บผลที่ผ่านตรวจแล้ว; retry และ refresh ไม่สุ่มใหม่.

รูปแบบผลสำหรับลูกค้า: **ตอบตรงคำถาม 1–2 ประโยค → เหตุผลจากไพ่และตำแหน่ง → ใบขยายเพิ่มอะไร → เงื่อนไข/สิ่งที่ยังสรุปไม่ได้ → สิ่งที่ทำหรือสังเกตได้จริง**. ไม่จำเป็นต้องเล่าทุกหมวดหรือทุกความหมายของแต่ละใบ.

### คำถามกำกวมและเรื่องความสัมพันธ์

- “จะเลิกกันไหม” ไม่เท่ากับ “ควรเลิกไหม”: อันแรกถามแนวโน้ม อันหลังถามทางเลือก. “เขารักไหม” ไม่เท่ากับ “เขาพร้อมคบจริงจังไหม”. เก็บ intent ให้แยกกัน.
- ผังอดีต/ปัจจุบัน/อนาคตเหมาะกับการมองเส้นทางความสัมพันธ์ แต่ไม่ตอบทุกเจตนาได้เท่ากัน. อย่าเปลี่ยนหน้าที่ช่องปัจจุบันให้กลายเป็น “ใจเขา” หลังเปิดไพ่แล้ว. หากเพิ่มผังเฉพาะความสัมพันธ์ในอนาคต ต้องให้ลูกค้าเห็นหน้าที่แต่ละช่องก่อนสุ่มและให้เจ้าของอนุมัติกฎแยก; v1 คงผังเดิมและระบุข้อจำกัดของการอนุมานความรู้สึกบุคคลอื่น.
- ไม่ใช้คำว่า “เลิก/นอกใจ/กลัว” ในข้อความเป็นตัวกำหนดผลลบ. ใช้คำถามเพื่อเลือกเลนส์ แต่ใช้ไพ่กับกฎที่อนุมัติกำหนดเนื้อหาคำอ่าน.
- ถ้าประโยคกลับขั้ว เช่น “จะไปต่อได้ไหม” กับ “จะจบไหม” ให้คงภาพความสัมพันธ์ตามไพ่เดิม แต่คำตอบตรงคำถามต้องเปลี่ยนให้ตรงขั้ว ไม่ตอบ “ใช่” เหมือนกันทั้งคู่.
- ถ้าขาดบริบทที่เปลี่ยนความหมายจริง ให้ถามสั้น ๆ หนึ่งข้อ เช่น “คนนี้เป็นแฟนปัจจุบัน คนคุย หรือแฟนเก่า?” และกำหนดช่วงเวลาที่ผู้ใช้ตั้งใจพิจารณา. ทำก่อนใช้เครดิต.
- ตอบคำถามรัก/เลิกได้โดยระบุว่าเป็นการอ่านสัญลักษณ์และแนวโน้ม; ไม่ต้องปฏิเสธทุกคำถามที่อ่อนไหว. ไม่ยืนยันข้อเท็จจริงว่ารู้ใจคนอื่น มีชู้ หรือเกิดเหตุการณ์เฉพาะจากหน้าไพ่.
- ไม่บังคับบวกทุกครั้ง: หากไพ่และกฎชี้ความตึงเครียด ให้ตอบตรง พร้อมเงื่อนไขและเหตุผล. ถ้าคำถามเกี่ยวกับสุขภาพ ความรุนแรง หรืออันตรายจริง ให้แยกการช่วยเหลือจากการทำนาย และไม่ใช้ไพ่ตัดสินความปลอดภัย.

**วันเกิด:** ไม่ต้องเก็บสำหรับ v1 นี้. ข้อมูลที่ช่วยเลือกความหมายคือสถานะความสัมพันธ์ เจตนาคำถาม และช่วงเวลาที่ถาม. ถ้าจะมีโหราศาสตร์วันเกิดภายหลัง ควรเป็นวิธีอ่านแยกที่มีแหล่งความรู้ของเจ้าของ ไม่ใช้เป็นเหตุผลอ้างว่าไพ่แม่นขึ้น. กติกาโปรเจกต์ปัจจุบันให้เก็บข้อมูลส่วนบุคคลในเครื่อง; งานนี้ไม่ส่งคำถามจริงให้ AI ภายนอก.

### ฐานข้อมูลที่ควรต่อจากร่างเดิม

ตารางเดิมรองรับบางส่วนแล้ว แต่การมีตารางไม่เท่ากับมี engine ที่ทำงาน:

| ส่วนเดิม | ข้อเสนอเพิ่ม/ปรับ |
|---|---|
| `card_meanings` | มี card/topic/situation/position/orientation/version/review แล้ว; เพิ่ม intent ถ้าจำเป็นและโครงหลักฐาน/ข้อสรุปที่อนุญาต แยก claim หรือ signal ที่ตรวจสอบได้จากคำบรรยายยาว |
| `reading_templates` | ใช้สำนวนและโครงคำตอบ; เพิ่มกฎประกอบที่มีเงื่อนไขและผลที่ชัดเจน (`interpretation_rules`) ไม่ถือว่าข้อความ template อย่างเดียวคือกฎเชื่อมไพ่ |
| `spreads`, `spread_positions` | ระบุ spread รุ่น 3+1 และตำแหน่งขยายที่ optional; แยกจำนวนขั้นต่ำ 3 / สูงสุด 4 พร้อมความสัมพันธ์ `clarifies=future` |
| `readings` | ร่างนี้ยังไม่มี `spread_id` โดยตรง; เพิ่ม spread/version, intent, normalized scope, horizon และสถานะล็อกคำถาม/สำรับ เพื่อไม่ต้องตีความย้อนหลังจาก service ที่อาจถูกแก้ |
| `reading_cards` | รองรับช่อง 4 และการอ้างใบที่ขยาย; บันทึก shuffle/deck commitment ฝั่ง server, การเลือก/เปิดครั้งเดียว และข้อกำหนดไม่ซ้ำใน reading เดียว |
| `reading_results` | เดิมใช้ `reading_id` เป็น PK จึงมีได้ผลเดียว; รองรับ revisions หรือส่วนขยายแบบ append-only เพื่อคงคำอ่านก่อนเพิ่มใบ 4 พร้อม evidence/rule IDs และรุ่น engine |
| `service_prices`, `credit_ledger`, `entitlements` | ใช้รับแพ็กครั้ง; เพิ่มแพ็ก/สิทธิ์ตามช่วงเวลา และ `usage_events` ที่กันใช้ซ้ำด้วย idempotency key. เครดิต/สิทธิ์ต้องตรวจและใช้ใน transaction ฝั่ง server |

ก่อนเก็บเงินจริง ต้องมี server/API ที่อ่านความหมายและตรวจสิทธิ์ได้. Vercel ที่ deploy ตอนนี้ยังเป็น static export. การล็อกสำรับ, กดใบขยายซ้ำ, retry คำอ่าน, หักเครดิตและ webhook ต้องออกแบบร่วมกัน; การซ่อนคำอ่านด้วย CSS ฝั่ง browser ไม่ใช่ระบบสิทธิ์. หากสร้างคำอ่านไม่สำเร็จ ให้คืนสิทธิ์หรือให้ retry โดยไม่หักครั้งซ้ำ. ระยะใช้แพ็กใหม่หมดได้ แต่ไม่ควรทำให้คำอ่านที่ซื้อไปแล้วหายตามอายุแพ็ก.

### ราคา: สมมติฐานสำหรับทดลอง ไม่ใช่ผลวิจัยความเต็มใจจ่าย

ราคาที่เจ้าของเสนอ: 69/1 คำถาม, 99/3 คำถาม, 199/ไม่อั้น 7 วัน, 399/ไม่อั้น 1 เดือน. แพ็ก 99 บาทเฉลี่ย 33 บาท/คำถาม ลดประมาณ 52.2% เทียบซื้อเดี่ยว 69 บาท; อาจทำให้ราคาเดี่ยวดูไม่คุ้ม จึงควรตั้งใจว่าจะใช้เป็นโปรเปิดตัวหรือราคาแพ็กถาวร.

**ข้อเสนอเริ่มทดลอง:**

| แพ็ก | ราคา | สิทธิ์คำถามใหม่ | อายุใช้สิทธิ์ | ราคาเฉลี่ยเมื่อใช้ครบ |
|---|---:|---:|---|---:|
| ครั้งเดียว | 69 บาท | 1 | อ่านครั้งนี้ | 69 บาท |
| แพ็ก 3 คำถาม | 149 บาท | 3 | 30 วัน | 49.67 บาท |
| สัปดาห์ | 199 บาท | 7 | 7 วัน | 28.43 บาท |
| เดือน | 399 บาท | 20 | 30 วัน | 19.95 บาท |

- ช่วงเปิดตัวอาจใช้ 99 บาท/3 คำถาม ครั้งแรกต่อบัญชี แล้ววัดผลเทียบ 149 บาท. ข้อจำกัดและวันเริ่มนับต้องชัดก่อนจ่าย; เสนอให้นับแพ็กตามเวลาชำระเงินสำเร็จ.
- เริ่มขายเพียงแพ็ก 1 และ 3 ก่อนเพื่อลดตัวเลือกและวัดการกลับมาใช้จริง; สัปดาห์/เดือนเป็นขั้นถัดไป. ราคาเหล่านี้ต้องทดลองกับผู้ใช้ ยังไม่มีข้อมูลต้นทุนหรือ conversion จริงยืนยัน.
- **หนึ่งคำถาม** = ประเด็นเดียว + ไพ่ 3 ใบ + ใบขยายอนาคต 1 ใบ + สรุปเฉพาะคำถาม + ขออธิบายผลเดิมเพิ่มได้ 2 ครั้งโดยไม่จั่วใหม่. เปลี่ยนคน/ประเด็น/บริบทสาระสำคัญ = reading ใหม่. “2 ครั้ง” เป็นข้อเสนอที่ต้องวัดต้นทุนและความพอใจ.
- ไม่แนะนำไม่อั้นตั้งแต่เริ่ม: ไม่รู้การใช้ระดับสูง ต้นทุน retry/support และความถี่ถามซ้ำ. หากกำหนดจำนวนต่อวัน ต้องแสดงจำนวนจริง ไม่ใช้คำว่า “ไม่อั้น” แล้วซ่อนเพดานไว้.
- แยกต้นทุนต่อคำอ่านสำเร็จให้รวม AI/retries, ระบบ, ค่ารับเงิน, support และคืนเงิน. สูตรประเมินต่อผู้ใช้: รายรับสุทธิ − จำนวนคำอ่าน × ต้นทุนผันแปรต่อคำอ่าน − ต้นทุนอื่นที่จัดสรร. อย่าตั้งจากค่า token อย่างเดียว.
- วัด conversion/การใช้สิทธิ์ครบ/การกลับมาใช้/คืนเงิน/ต้นทุนและจำนวนอ่านกลุ่มใช้งานสูง แล้วค่อยปรับจำนวนสิทธิ์หรือราคา. คำอ่านเชิงไพ่ที่ตรงฐานข้อมูลกับความพอใจเป็นคนละตัวชี้วัด; อย่าใช้คะแนน “ตรงใจ” เป็นหลักฐานยืนยันการพยากรณ์.

### เกณฑ์ก่อนเริ่มสร้างและขาย

1. ให้เจ้าของทบทวนความหมายหมวดรักและนิยามใบ 4 รวมทั้งกฎเมื่อไพ่ขัดกัน; ตัวอย่างในเอกสารนี้ไม่กลายเป็น approved โดยอัตโนมัติ.
2. ทำเคสคำถามแต่งขึ้นพร้อมไพ่คงที่ประมาณ 30 เคส โดยมีทั้งบวก ลบ ผสม และข้อมูลไม่พอ. ให้แม่หมอเขียนข้อสรุป/หลักฐาน/สิ่งที่ห้ามอนุมานเป็นคำตอบอ้างอิง.
3. ตรวจคำถามต่างสำนวน, กลับขั้ว yes/no, ไพ่เดิมเปลี่ยนตำแหน่ง, เปลี่ยนใบอนาคต, เปลี่ยนใบขยาย, กรณีไม่มีฐานความรู้ และคำถามที่พยายามสั่ง AI ให้ละเลยกฎ. สาระต้องเปลี่ยนตามปัจจัยที่ถูกต้องและไม่สร้างข้อเท็จจริงเพิ่ม.
4. ตรวจในระบบจริงว่าใบ 4 ไม่ซ้ำ/ไม่เปลี่ยนสามใบแรก, เปิดได้ครั้งเดียว, refresh/retry ได้ผลเดิม, ผู้ใช้อื่นอ่านผลไม่ได้, ซื้อ/หักสิทธิ์ซ้ำไม่ได้, จ่ายแล้วสร้างผลล้มเหลวมีทางคืนสิทธิ์.
5. เมื่อคุณภาพคำอ่านผ่าน จึงทำ server/payment และทดลองราคา. ยังไม่จำเป็นต้องทำทั้ง 66 ตารางหรือทุกหมวดพร้อมกัน.

## แบบเก็บความรู้และสำนวนแม่หมอ กับระดับ RAG ที่ควรเริ่ม — 2026-10-18

**สถานะ: สเปกแบบกรอกและสถาปัตยกรรมสำหรับพิจารณา.** ยังไม่ได้สร้าง Google Sheet, แบบฟอร์ม, chatbot, vector store หรือเชื่อมบริการถอดเสียง. คำขอรอบนี้คือให้แนะนำวิธีเก็บความรู้จากแฟนเจ้าของและประเมินความจำเป็นของเทคโนโลยี.

### วิธีเก็บที่เสนอ

ให้แม่หมอกรอกหรือพูด **ทีละเคส** ส่วนผู้ดูแลจัดข้อมูลเป็นตาราง. เริ่มจาก Excel ในเครื่องหรือข้อมูลตัวอย่างที่ไม่มีข้อมูลลูกค้าจริง; ถ้าจะใช้ Sheets ให้ใช้เฉพาะความรู้ทั่วไป/เคสสมมติที่อนุญาตให้ขึ้นบริการภายนอก. กติกาโปรเจกต์ปัจจุบันให้ข้อมูลส่วนบุคคลอยู่ในเครื่อง. ไม่ควรเริ่มด้วยเมทริกซ์ที่ให้แม่หมอกรอกทุกหมวด × สถานการณ์ × ตำแหน่ง × ประเภทคำถาม; เติมเฉพาะฐานและข้อยกเว้นที่มีสาระ แล้วขยายจากช่องว่างที่พบตอนทดสอบ.

โครงสมุดงานที่เสนอ 5 แท็บ (ยังไม่ได้สร้างไฟล์):

| แท็บ | หนึ่งแถวหมายถึง | ช่องสำคัญ |
|---|---|---|
| ความหมาย | ความหมายหนึ่งใบในบริบทหนึ่ง | ไพ่, หมวด, สถานการณ์, ตำแหน่งที่ใช้/ทั่วไป, ประเภทคำถามที่เกี่ยวข้อง, ความหมาย, ข้อห้ามอนุมาน, ที่มา, สถานะทบทวน |
| เคสอ่านไพ่ | คำถามหนึ่งข้อกับไพ่ตามตำแหน่งที่กำหนด | คำถาม, บริบท/ช่วงเวลา, ไพ่ 1–3, คำตอบก่อนใบ 4, ใบ 4, คำตอบหลังใบ 4, หลักฐานรายใบ, ข้อที่ยังสรุปไม่ได้ |
| กฎอ่านร่วมกัน | เงื่อนไขและข้อสรุปหนึ่งกฎ | ใช้กับบริบทใด, ไพ่/สัญญาณและตำแหน่ง, อ่านร่วมกันอย่างไร, เงื่อนไขยกเว้น, เคสต้นทาง, แม่หมอทบทวนแล้วหรือยัง |
| สำนวนแม่หมอ | ตัวอย่างภาษาหรือการแก้คำตอบหนึ่งคู่ | สถานการณ์การพูด, ข้อความเดิม, แม่หมอแก้เป็น, เหตุผลที่แก้, ประโยคที่ชอบ/ไม่ใช้, ขอบเขตใช้ได้ |
| เคสตรวจระบบ | เคสอ้างอิงที่กันไว้ตรวจโดยเฉพาะ | input/ไพ่, คำตอบอ้างอิง, ประเด็นที่ต้องมี, ข้อที่ห้ามเพิ่ม, ผลตรวจความหมาย/ความตรงคำถาม/น้ำเสียง |

ใช้รหัสไพ่จาก catalog เดิม; ให้ระบบหรือผู้ดูแลเติม `record_id`, `case_family_id`, `source_type`, `source_ref`, `knowledge_version`, `style_version`, `review_status`, `reviewed_by`, `reviewed_at`. แม่หมอไม่ต้องคิดเลขรุ่นเอง. คำแก้ไขควรแยกเป็น **แก้ความหมาย / แก้สำนวน / แก้ทั้งสอง** เพื่อไม่ให้การปรับภาษาไปเปลี่ยนกฎอ่านโดยไม่รู้ตัว. เก็บคำตอบต้นฉบับของแม่หมอกับฉบับจัดรูปแยกกัน.

### แบบกรอกหลักที่ให้แม่หมอเห็น

1. **ลูกดวงถามว่าอะไร?** ใช้คำถามจริงที่ลบรายละเอียดระบุตัวบุคคล หรือคำถามสมมติ; หนึ่งประเด็นต่อเคส.
2. **รู้อะไรเกี่ยวกับสถานการณ์บ้าง?** สถานะความสัมพันธ์ ช่วงเวลาที่ถาม และข้อมูลที่ผู้ถามบอกจริง; เว้นสิ่งที่ไม่รู้ไว้ ไม่เติมให้ครบเอง.
3. **ออกไพ่ไหนในช่องอะไร?** ใช้รายการเลือกชื่อไพ่และผังเดิม; รุ่นแรกตั้งตรงตามระบบปัจจุบัน.
4. **ถ้าเป็นลูกดวงอยู่ตรงหน้า แม่หมอจะตอบว่าอะไร?** ให้พูดหรือเขียนตามธรรมชาติเต็มคำตอบก่อนปรับภาษา.
5. **ข้อสรุปสำคัญแต่ละข้ออิงไพ่/ตำแหน่งไหน?** ขอคำอธิบายสั้นที่ตรวจสอบได้ รวมสิ่งที่ไพ่สนับสนุนและสิ่งที่ขัดกัน.
6. **มีอะไรที่ยังตอบไม่ได้ หรือจำเป็นต้องถามเพิ่ม?** รวมประโยคที่แม่หมอจะไม่ใช้กับเคสนี้และคำแนะนำที่ทำได้จริง.

ช่องใบขยายเป็นส่วนต่อจากข้อ 3–5: ให้แม่หมออ่านสามใบให้จบก่อน แล้วค่อยเห็นใบที่ 4. เก็บ **คำตอบก่อน / คำตอบหลัง / ประเด็นที่เปลี่ยน / ประเด็นที่คงเดิม**. ถ้าเก็บแต่คำตอบสี่ใบสุดท้าย จะไม่เห็นว่ากฎขยายทำงานอย่างไร. ไม่ต้องบังคับให้ใบ 4 เปลี่ยนข้อสรุปทุกครั้ง.

### ตัวอย่างคำถามสำหรับเก็บสำนวน

ถามให้แม่หมอเลือกหรือแก้เอง ไม่ถือว่าคำที่เอเจนต์เสนอเป็นสไตล์ของแม่หมอ:

- เรียกผู้ถามว่าอะไร และแทนตัวเองอย่างไร?
- ถ้าไพ่ชี้ความขัดแย้ง จะตอบตรงระดับไหนและปิดท้ายอย่างไร?
- ถ้าคำตอบยังไม่ชัด จะพูดว่าอะไรโดยไม่อ้อมจนไม่ตอบคำถาม?
- มีคำไหนไม่ใช้ เช่น คำรับประกัน คำตัดสินบุคคล หรือคำปลอบที่ฟังไม่เป็นตัวเอง?
- นำคำตอบที่แม่หมอไม่ชอบมาให้แก้ แล้วระบุว่าปัญหาคือเนื้อหาไม่ตรงไพ่หรือภาษาผิดน้ำเสียง.

ตัวอย่างโครงคู่แก้ไข: ข้อความที่ไม่ยอมรับ → ข้อความที่แม่หมอเขียนใหม่ → เพราะเหตุใด → ใช้กับบริบทไหน. ต้องมีเนื้อหาและเหตุผลจริงจากแม่หมอ ไม่เก็บเพียงคำลงท้ายหรือคำติดปาก. ถ้าการแก้เพิ่มข้อสรุปใหม่ ต้องอ้างไพ่/กฎและทบทวนความหมายด้วย.

### วิธีเริ่มโดยไม่ให้แม่หมอทำงานมากเกินไป

**ข้อเสนอทดลอง:** เริ่มหมวดความรัก 30 เคสสมมติที่คัดให้ครอบคลุมคำถามและผลหลายแบบ; ใช้ 20 เคสพัฒนาระบบและกันอีก 10 เคสไว้ตรวจ. จำนวนนี้เป็นจุดเริ่มทำงาน ไม่ใช่เกณฑ์ว่าข้อมูลเพียงพอเปิดขายครบ 78 ใบ. คลังเดิม 468 ข้อความยังต้องทบทวนตามขอบเขตบริการที่จะเปิด.

เลือกทั้งคำถามความรู้สึก/ความจริงจัง/คืนดี/เลิก/ทิศทาง และไพ่ที่หนุนกัน ขัดกัน หรือยังไม่พอจะสรุป. ทำเคสเปรียบเทียบที่เปลี่ยนเพียงอย่างเดียว เช่น ไพ่ชุดเดิมแต่เปลี่ยนสถานะ หรือบริบทเดิมแต่เปลี่ยนเฉพาะใบอนาคต/ใบขยาย. เคสใกล้เคียงและคำถามต่างสำนวนในตระกูลเดียวกันให้อยู่ฝั่งพัฒนาหรือฝั่งตรวจด้วยกัน เพื่อไม่ให้ข้อสอบซ้ำกับตัวอย่างที่ระบบเห็น.

ก่อนทดสอบให้ตรึงรุ่นความรู้และข้อสรุปอ้างอิง. เคสตรวจต้องไม่เข้า retrieval หรือ prompt ตัวอย่าง; ถ้านำเคสตรวจมาใช้แก้ระบบแล้ว ควรมีชุดตรวจใหม่ที่ยังไม่ถูกใช้. ให้แม่หมอให้คะแนนแยกความตรงไพ่ ความตรงคำถาม และความเป็นสำนวนตัวเอง พร้อมระบุข้อผิดพลาด ไม่รวมเป็นคะแนน “แม่น” ตัวเดียว. คะแนนตรงใจไม่ใช่หลักฐานยืนยันเหตุการณ์อนาคต.

### ระบบตอบที่ควรเริ่ม

ข้อเสนอ v1: `คำถาม/บริบทและไพ่ที่ตรึงแล้ว → ค้นความหมายและกฎที่ approved ด้วยรหัส/เงื่อนไข → เลือกตัวอย่างสำนวนที่เกี่ยวข้อง → สร้างคำตอบ → ตรวจข้ออ้างกับหลักฐาน → บันทึกผลและรุ่นความรู้/สำนวน`.

- ไพ่และตำแหน่งเป็นข้อมูลที่รู้แน่นอน จึงดึงข้อมูลด้วยรหัสและตัวกรองจากฐานข้อมูลก่อน. **ห้ามให้ความคล้ายของ embedding เลือกความหมายของไพ่คนละใบมาเป็นหลักฐานแทน.** เลือกเฉพาะกฎที่เงื่อนไขตรงและความรู้รุ่นที่เผยแพร่.
- กรณีไม่มีความหมายตรงตำแหน่ง ให้ใช้เฉพาะความหมายทั่วไปในหมวดเดียวกันที่อนุมัติว่าใช้ได้ พร้อมกฎตำแหน่งที่อนุมัติ; หากไม่มีให้แจ้งช่องว่าง ไม่ข้ามไปใช้หมวดอื่น.
- แยก **หลักฐานคำอ่าน** ออกจาก **ตัวอย่างสำนวน** ในข้อมูลที่ส่งให้ตัวสร้างคำตอบ. เคสคล้ายกันอาจช่วยจัดภาษา แต่ไม่ให้นำประวัติคน ผลลัพธ์ หรือข้อสรุปของเคสนั้นมาทับไพ่ปัจจุบัน. ตัวอย่างสำนวนก็ต้องผ่านการทบทวนและตรงขอบเขต.
- RAG คือกระบวนการดึงข้อมูลมาประกอบการสร้างคำตอบ; สำหรับข้อเสนอนี้สามารถดึงข้อมูลแบบมีโครงสร้างก่อน โดยไม่ต้องมีฐานเวกเตอร์แยก. หน้าแชตเป็นรูปแบบ UI คนละส่วนกับการค้นข้อมูล จึงเพิ่ม RAG ให้หน้าผลไพ่ได้โดยไม่ทำแชตบอตเต็มรูปแบบ.
- การอ้าง ID ที่มีอยู่ไม่พอจะรับประกันว่าเนื้อหาถูกต้อง ต้องตรวจว่าข้อสรุปนั้นตามมาจากหลักฐานจริงและไม่มีรายละเอียดใหม่. คำถามอิสระเป็นข้อมูล ไม่ใช่คำสั่งให้ข้ามกฎ. คำอ่านเดิมควรเก็บเป็น snapshot; การแก้ KB ภายหลังไม่เปลี่ยนผลที่ขายไปเงียบ ๆ.

| ส่วนประกอบ | ข้อเสนอสำหรับตอนนี้ | เพิ่มเมื่อใด |
|---|---|---|
| ตารางความรู้ + กฎ + รุ่นเผยแพร่ | ทำก่อน | จำเป็นต่อการตรวจสอบคำอ่าน |
| ตัวอย่างสำนวนของแม่หมอ | ทำก่อน | ใช้คำตอบและคู่แก้ไขที่เจ้าของทบทวน |
| Embedding / vector store | เตรียมโครงรองรับ แต่ยังไม่ต้องติดตั้ง | เคสมีความหลากหลาย และผลทดสอบพบว่าการค้นด้วยหมวด/intent/คำค้นหาเคสที่ควรเจอไม่พบ |
| Hybrid search | ประเมินกับชุดตรวจภายหลัง | ต้องค้นทั้งชื่อไพ่/คำเฉพาะและความหมายของภาษาพูด เช่น “เขาหาย” กับ “การเว้นระยะ” |
| Reranker | ยังไม่ต้องเพิ่มแยก | ดึงรายการที่เกี่ยวข้องมาได้แล้ว แต่ลำดับบนยังไม่ตรง; ต้องวัดว่าดีขึ้นคุ้มกับเวลา/ต้นทุน |
| แชตถามต่อ | ภายหลังหน้าผลพื้นฐานทำงานดี | ต้องการอธิบายผลเดิมเพิ่ม โดยตรึง reading/ไพ่/รุ่นความรู้ |
| Whisper / STT | มีประโยชน์เป็นตัวเลือกสำหรับคนกรอก | แม่หมอพูดได้สะดวกกว่าพิมพ์; ไม่จำเป็นต้องรอแชตบอตลูกค้า |

**ข้อมูลความสามารถจาก OpenAI Docs ที่ตรวจ 2026-10-18:** hosted vector store สามารถ chunk/embed/index ไฟล์ให้อัตโนมัติ; File Search รองรับ semantic และ keyword search; Retrieval มี metadata filters และตัวเลือก ranking/hybrid weighting. จึงไม่จำเป็นต้องต่อ pipeline ทุกชิ้นเองหากภายหลังเลือกบริการนี้ แต่ยังต้องออกแบบข้อมูล สิทธิ์เข้าถึง การกรองรุ่นและการทดสอบของเราเอง. ถ้าใช้ metadata ระดับไฟล์ ต้องแบ่งเอกสารให้สอดคล้องกับการกรอง ไม่ถือว่าโยนทั้งสมุดงานเข้าไฟล์เดียวแล้วกรองความหมายรายแถวได้เอง. งานนี้ไม่ได้เลือก provider หรืออัปโหลดข้อมูล. แหล่ง: [Retrieval](https://developers.openai.com/api/docs/guides/retrieval), [File Search](https://developers.openai.com/api/docs/guides/tools-file-search).

### เสียงสำหรับเก็บความรู้

เสนอ flow: `อัดเสียงเคสสมมติ → ถอดเสียงเป็นข้อความ → ตรวจชื่อไพ่/คำปฏิเสธ/ตำแหน่ง → แยกเข้าช่องร่าง → แม่หมอแก้และรับรอง → เผยแพร่เข้าคลัง`.

เก็บทั้งข้อความถอดตรงและฉบับแม่หมอแก้แล้ว; อย่าให้ตัวสรุปปรับสำนวนก่อนเก็บต้นฉบับ. STT ทำหน้าที่ถอดเสียง ไม่ได้สร้างกฎอ่านไพ่หรือทำให้ระบบเรียนรู้ความรู้โดยอัตโนมัติ. ไม่ใช้การถอดเสียงนี้เป็นการโคลนเสียง.

ตรวจพบ `whisper-cli` ในเครื่องที่ `/opt/homebrew/bin/whisper-cli`; ยังไม่ได้ตรวจโมเดล/รันกับเสียงแม่หมอหรือเชื่อมเข้าระบบ. เสนอเริ่มถอดในเครื่องตามกติกาข้อมูลส่วนบุคคล. เอกสาร OpenAI อธิบาย Whisper ผ่านบริการถอดเสียง แต่เป็นคนละวิธีติดตั้งกับ CLI ในเครื่อง; ความถูกต้องต้องตรวจจากเสียงไทยและชื่อไพ่ที่ใช้จริง. แหล่งหน้าที่ STT: [File transcription](https://developers.openai.com/api/docs/guides/speech-to-text).
